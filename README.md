# ПОС — преподавательская оценка студентов

Консольный модуль учёта оценок: студенты, рубрикатор критериев, оценки и итог по весам.
Домашнее задание №2 по курсу «Конструирование программного обеспечения»: DDD, архитектура
Ports & Adapters (гексагональная) и паттерны GoF.

## Запуск

Нужен Python 3.12+.

Windows (PowerShell):

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m pos
```

Linux / macOS:

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pos
```

Данные хранятся в папке `pos-data` текущего каталога (`students.json` и `rubric.json`) и
переживают перезапуск. Другую папку можно передать аргументом: `python -m pos D:\курс-кпо`.

Проверки:

```bash
python -m pytest --cov
python -m ruff check src tests
python -m ruff format --check src tests
python -m mypy src tests
```

## Как пользоваться

Главное меню:

| Пункт | Что внутри |
|---|---|
| 1. Студенты | список, добавить, переименовать, удалить (вместе с оценками) |
| 2. Рубрикатор | список критериев с долей в итоге, добавить, изменить название или вес, удалить |
| 3. Оценки | выставить, посмотреть оценки студента, исправить, отменить |
| 4. Итоги | итог одного студента с разбивкой по критериям, итоги всех студентов |
| 5. Импорт ведомости | загрузка оценок из CSV или JSON |
| 6. Экспорт итогов | сохранение итогов в CSV или JSON |

Перед выбором студента или критерия консоль показывает список с ID. Числа можно вводить с
точкой или с запятой. Дата оценки вводится как `ДД.ММ.ГГГГ`, Enter означает «сегодня».
Комментарий необязателен.

### Ведомость CSV

Первая строка содержит заголовок: столбец студента, затем названия критериев из рубрикатора.
Разделитель (`,`, `;` или табуляция) определяется по заголовку, поэтому подходит и выгрузка
из русского Excel с `;` и десятичной запятой. Пустая ячейка означает «оценки нет».

```csv
Студент;ДЗ-1;ДЗ-2;Контрольная;Экзамен
Иванов Иван;8;9;15,5;72
```

### Ведомость JSON

```json
{"students": [{"name": "Иванов Иван", "scores": {"ДЗ-1": 8, "Экзамен": 72}}]}
```

`null` в оценке означает «оценки нет».

Правила импорта:

- Студент ищется по имени без учёта регистра. Если его нет, он добавляется.
- Если оценка по критерию уже стоит, она исправляется.
- Каждая ячейка проверяется отдельно, отчёт показывает принятые ячейки и отказы с причиной.
- Ошибка структуры файла (битый JSON, лишние значения в строке CSV, повтор критерия в
  заголовке) отменяет весь импорт до того, как что-либо записано.

### Экспорт

Формат выбирается по расширению. `.csv` содержит столбцы ID, студент, итог, число
оценённых критериев и всего критериев; файл пишется в UTF-8 с BOM, чтобы Excel открыл
кириллицу. `.json` дополнительно содержит название правила итога.

## Демонстрационный сценарий

Сценарий «завести студентов и критерии → выставить оценки → получить итог → экспорт»,
файлы ведомостей лежат в `samples/`.

1. **Рубрикатор → Добавить критерий**, четыре раза:

   | Критерий | Макс. | Вес |
   |---|---|---|
   | ДЗ-1 | 10 | 0,2 |
   | ДЗ-2 | 10 | 0,2 |
   | Контрольная | 20 | 0,2 |
   | Экзамен | 100 | 0,4 |

   В «Списке критериев» видны доли 20/20/20/40 %.

2. **Импорт ведомости** → `samples/statement.csv`. Студенты добавляются сами, итог
   «Принято 10 из 12». Два отказа показывают инварианты:
   - «Доклад» → `критерия «Доклад» нет в рубрикаторе`;
   - ДЗ-2 = 12 → `балл 12 вне диапазона критерия: от 0 до 10`.

3. **Импорт ведомости** → `samples/statement.json`: у Иванова экзамен исправляется
   (`72 → 78`), добавляется Кузнецова Мария.

4. **Студенты → Добавить** — можно завести студента вручную, затем
   **Оценки → Выставить оценку**:
   - Сидорову по ДЗ-2 балл 11 — отказ: `балл 11 вне диапазона критерия: от 0 до 10`;
   - тот же балл 10 — оценка выставлена.

5. **Оценки → Исправить оценку**: Иванову экзамен 80, комментарий «апелляция».

6. **Итоги → Итоги всех студентов**:

   | Студент | Правило 1 (итоговая оценка) | Правило 3 (промежуточный) |
   |---|---|---|
   | Иванов Иван | 8 | 8.15 |
   | Петрова Анна | 9 | 9.44 |
   | Сидоров Пётр | 5 | 6.4 |
   | Кузнецова Мария | 5 | 8.33 |

7. **Экспорт итогов** → `итоги.csv` или `итоги.json`.

## Предметная область и DDD

### Единый язык

| Термин | В коде | Смысл |
|---|---|---|
| студент | `Student` | кого оценивают; корень агрегата, хранит свои оценки |
| критерий | `Criterion` | за что ставят балл: название, максимум, вес |
| рубрикатор | `Rubric` | набор критериев курса; корень агрегата |
| оценка | `Evaluation` | факт «студенту по критерию поставили балл», дата и комментарий по желанию |
| балл | `Score` | число баллов вместе с максимумом критерия |
| итог | `FinalGrade` | результат по студенту, вычисленный из оценок и рубрикатора |
| правило итога | `GradingPolicy` | формула, по которой оценки сводятся в итог |
| ведомость | `StatementEntry`, `StatementImport` | таблица оценок для импорта |

### Entity и Value Object

**Entity** различаются по идентичности, а не по значениям, и меняются со временем.

- `Student` остаётся тем же студентом после переименования.
- `Criterion` остаётся тем же критерием, если поменять название или вес: оценки ссылаются
  на него по `CriterionId`. Наружу выдаётся неизменяемый снимок сущности; при изменении
  рубрикатор заменяет снимок, сохраняя ID. Это Entity, а не VO: идентичность задаётся ID.
- `Evaluation` можно исправить, и это та же оценка. Её идентичность — критерий внутри
  студента: у студента одна текущая оценка на критерий.

**Value Object** неизменяемы (`frozen dataclass`) и равны, когда равны их значения.

- `StudentId` и `CriterionId`.
- `Score(points, out_of)`. Если исправить оценку, создаётся новый `Score`, а старый не
  меняется.
- `FinalGrade(value, evaluated, criteria)`.
- `Contribution(weight, share)` — вклад одного критерия в расчёт.

Пример: `Score(Decimal("8"), Decimal("10")) == Score(Decimal("8"), Decimal("10"))` — это одно
и то же значение, а два студента «Иванов Иван» с разными ID — разные сущности.

### Агрегаты и границы

- **Rubric** содержит критерии и следит, чтобы названия не повторялись (без учёта регистра),
  а максимум и вес были положительными. ID критериев выдаёт сам рубрикатор. Максимум после
  создания не меняется: по нему уже могли выставить оценки. Критерии неизменяемы снаружи;
  переименование и изменение веса проходят через методы рубрикатора.
- **Student** содержит свои оценки и следит, чтобы на критерий была одна текущая оценка.
  При добавлении оценки принимает рубрикатор и проверяет наличие критерия и совпадение
  максимума. Восстановление студента с оценками требует рубрикатор для тех же проверок.
  Исправить или отменить можно только существующую.

Агрегаты ссылаются друг на друга только по ID: оценка хранит `CriterionId`, а не объект
критерия.

### Инварианты и где они охраняются

| Правило | Где |
|---|---|
| балл не выходит за пределы критерия | `Score.__post_init__`: `0 ≤ points ≤ out_of`; `Evaluation.validate_against` сверяет балл и максимум с критерием при добавлении в `Student`; при исправлении `Score.with_points` проверяет тот же максимум |
| оценку можно выставить только по критерию из рубрикатора | `EvaluationFactory.create` берёт критерий из `Rubric`; `Student.grade` повторно проверяет связь через `Evaluation.validate_against`, даже при создании оценки без фабрики |
| нельзя удалить критерий, по которому есть оценки, иначе появятся оценки по несуществующему критерию | `ensure_criterion_unused` в `domain/services.py`, вызывается сценарием удаления |
| итог согласован с текущими оценками | итог нигде не хранится, `FinalGradeCalculator` проверяет соответствие оценок рубрикатору и считает результат заново |
| итог в пределах 0–10 | `FinalGrade.__post_init__` |
| одна текущая оценка на критерий | `Student.grade` |

Нарушение любого правила — `DomainError` с понятным текстом, консоль показывает его и
продолжает работу.

### Repository

Порты `StudentRepository` и `RubricRepository` объявлены в домене
(`domain/repositories.py`), реализации — снаружи:

- `adapters/json_storage.py` — JSON-файлы для приложения. Отображает домен в записи и
  обратно (маппинг DTO ↔ домен), пишет атомарно через временный файл. Битый файл
  отклоняется при запуске, а не перезаписывается. Только отсутствие файла означает
  пустое хранилище: `null`, `{}`, `[]`, `false` и другие неверные структуры отклоняются.
  Репозиторий студентов получает порт `RubricRepository` через DI и проверяет наличие
  критериев и максимумы оценок при загрузке и сохранении.
- `adapters/memory.py` — в памяти, для тестов.

### Domain Service

`FinalGradeCalculator` (`domain/services.py`). Итог не принадлежит ни студенту, ни
рубрикатору: нужны оба агрегата сразу. Сервис собирает по каждому критерию рубрикатора вклад
(вес и долю `балл / максимум`) и отдаёт его правилу итога.

Формула по умолчанию: `итог = 10 · Σ(вес · балл / максимум) / Σ весов`. Поэтому веса не
обязаны давать в сумме 1, а максимумы у критериев могут быть разными. Расчёт идёт в
`Fraction` без погрешности float. Например, при весах 0.1, 0.1, 0.2 и баллах 0, 0, 9 из 10
float даёт 4.4999999 вместо 4.5, и оценка округлилась бы до 4 вместо 5; тест
`test_exact_arithmetic_keeps_half_point_for_rounding`.

## Архитектура: Ports & Adapters

```
src/pos/
  domain/        сущности, VO, инварианты, правила итога, доменный сервис, порты репозиториев
  application/   сценарии (сервисы), DTO для внешнего мира, порты StatementSource и GradeSheetExporter
  adapters/      консоль, JSON-хранилище, хранилище в памяти, чтение ведомостей, запись итогов
  container.py   composition root: DI-контейнер собирает граф зависимостей
  __main__.py    точка входа
```

Зависимости направлены только внутрь:

```
        adapters  ──►  application  ──►  domain
 (console, json,       (сценарии, DTO,      (ничего не импортирует
  csv, memory)          порты ввода/вывода)   из внешних слоёв)

 container.py знает все слои и связывает реализации портов со сценариями
```

- **Домен** не знает про консоль, файлы, CSV и JSON. В `domain/` нет ни одного импорта из
  `application` или `adapters`.
- **Application** содержит сценарии:
  - `StudentService` — студенты;
  - `RubricService` — рубрикатор;
  - `GradingService` — выставить, исправить, отменить оценку, посчитать итог;
  - `StatementImport` — импортировать ведомость;
  - `GradeSheetExport` — экспортировать итоги.

  Наружу сценарии отдают неизменяемые DTO (`application/views.py`), поэтому консоль не
  может в обход правил менять сущности.
- **Порты**:
  - ведущий (driving) адаптер — консоль, она вызывает сервисы application;
  - ведомые (driven) порты: репозитории (в домене), `StatementSource` и
    `GradeSheetExporter` (в application).

  У каждого ведомого порта своя реализация в `adapters/`. У хранилища реализаций две, и
  тесты подменяют JSON на память через контейнер.
- **DI** — `dependency-injector`. Контейнер в `container.py` единственный знает конкретные
  классы. Тесты переопределяют провайдеры (`container.students.override(...)`), см.
  `tests/support.py`, `test_container.py`, `test_statement_import.py`.

## Паттерны GoF

Взято по одному паттерну из порождающих и структурных и два поведенческих. Каждый закрывает
конкретную проблему.

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `EvaluationFactory` (`domain/evaluation.py`) | Фабрика берёт критерий из рубрикатора и его максимум для `Score`. Это единая точка создания оценок в сценариях ручного выставления и импорта, чтобы не дублировать сборку объекта. Дополнительно агрегат `Student` проверяет соответствие оценки рубрикатору, даже если оценка создана напрямую. |
| Структурный | **Decorator** | `HalfUpRounding` (`domain/grading.py`) | Итоговую оценку округляют до целого арифметически: 6.5 → 7, тогда как встроенный `round` даёт 6. Округление — модификатор поверх любой формулы: `HalfUpRounding(WeightedTotal())` даёт итоговую оценку, а без обёртки получается точный балл. Без декоратора пришлось бы дублировать округление в каждой формуле или заводить флаги в сервисе. |
| Поведенческий | **Strategy** | `GradingPolicy` → `WeightedTotal`, `EvaluatedAverage` (`domain/grading.py`) | Правила итога разные: в конце курса невыставленная оценка считается нулём, а промежуточный итог считают только по выставленным оценкам. Доменный сервис не меняется, правило выбирается в консоли. Набор правил собирается в контейнере, новое правило — это новый класс плюс строка в `container.py`. |
| Поведенческий | **Template Method** | `StatementFile.read` (`adapters/statement_files.py`) | Импорт ведомостей устроен одинаково: прочитать файл (кодировка, ошибки) → разобрать в строки → развернуть в записи «студент, критерий, балл» без пустых ячеек. Отличается только шаг разбора, это абстрактный `_rows`, реализованный в `CsvStatementFile` и `JsonStatementFile`. Новый формат — один подкласс. |

Что сознательно не используется:

- **Builder** рубрикатора не нужен: рубрикатор собирается по одному критерию через `Rubric.add`.
- **Facade** не нужен: консоль работает с несколькими небольшими сервисами, ещё одна прослойка
  ничего бы не упростила.

## Решения и компромиссы

- **Оценки внутри агрегата студента**, а не отдельным агрегатом. Тогда правило «одна оценка
  на критерий» охраняется самим агрегатом, а удаление студента удаляет и его оценки.
- **Проверка удаления критерия** затрагивает два агрегата, поэтому это доменная функция
  `ensure_criterion_unused`. Её вызывает сценарий `RubricService.remove`.
- **Максимум критерия неизменяем**, а `Score` хранит его копию. Поэтому оценка всегда
  проверяет собственный диапазон. Совпадение копии максимума с рубрикатором проверяется
  при добавлении оценки, восстановлении из хранилища и расчёте итога.
- **Баллы и веса хранятся в `Decimal`** и записываются в JSON строками, чтобы не терять
  точность. Расчёт итога ведётся в `Fraction`, а в два знака итог округляется только при
  выводе.
- **Импорт добавляет незнакомых студентов**: ведомость обычно содержит весь список группы.
  Если в курсе два студента с одинаковым именем, импорт не угадывает и просит выставить
  оценку вручную по ID.
- **ID студентов не переиспользуются** после удаления: счётчик хранится в файле.

## Роль ИИ

Основной код приложения написан мной. ИИ (Codex) использовался для последующей проверки
готового локального решения по требованиям задания и для исправления найденных замечаний.

По результатам проверки с помощью ИИ внесены следующие изменения:

- Закрыт обход проверок через прямое создание `Evaluation`: агрегат `Student` проверяет
  существование критерия и соответствие максимума оценки рубрикатору. Эти проверки также
  выполняются при восстановлении, сохранении и расчёте итога.
- Исправлена загрузка JSON-хранилища: неверные структуры больше не принимаются за пустые
  данные; оценки с неизвестными критериями или несовпадающими максимумами отклоняются.
- Закрыт обход уникальности названий через изменение выданного критерия: наружу возвращаются
